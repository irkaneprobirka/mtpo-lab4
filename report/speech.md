## 1. Тема

Здравствуйте. В работе я сравнила Jest, Vitest и Mocha на примере консольного приложения. Меня интересовало, сколько времени, процессорных ресурсов и памяти нужно каждому инструменту для выполнения одного и того же набора тестов.

## 2. Проблема

Для одного приложения можно использовать разные фреймворки тестирования. Все они запускают проверки, но затраты на выполнение могут отличаться. Поэтому задача работы — подготовить одинаковые тесты, сравнить три инструмента и выбрать наиболее подходящий для этого приложения. В сравнение включаются только запуски, в которых успешно прошли все 99 тестов.

## 3. Что делает приложение

Программа принимает строку или файл JSON с несколькими строками. Она находит самый длинный палиндром, его длину и общее количество палиндромных вхождений. Например, для abba ответ — abba, длина четыре, количество шесть. Пользователь может передать свои данные, заранее задавать правильный ответ ему не нужно.

**В этот момент показать в терминале:**

```powershell
npm run start -- "abba"
```

Если есть время, также показать файл:

```powershell
npm run start -- --file data/example.json
```

## 4. Алгоритм Манакера

Палиндром читается одинаково в обе стороны. Манакер использует уже найденную симметрию, чтобы не сравнивать одни и те же символы заново. Разделители помогают одинаково обрабатывать палиндромы чётной и нечётной длины. Для abba учитываются четыре отдельных символа, bb и abba — всего шесть вхождений. Время и дополнительная память алгоритма растут линейно с длиной строки.

## 5. Для чего нужны фреймворки

Jest предоставляет готовые средства для проверки функций, серверного кода и компонентов интерфейса JavaScript-приложений. Vitest подходит для JavaScript и TypeScript и удобен в проектах с Vite, потому что может использовать настройки сборки приложения. При этом он работает и с программами Node.js. Mocha запускает тесты, а средства сравнения полученных и правильных ответов к нему выбираются отдельно. Области применения пересекаются: все три подходят для нашей консольной программы. Здесь везде используется один и тот же assert из Node.js.

## 6. Что проверяют тесты

В каждом фреймворке выполняются одинаковые 99 тестов. Они проверяют обычные строки, пустую строку, повторяющиеся символы, русские буквы, пробелы и эмодзи. Также проверяются чтение JSON, ошибки во входе, вывод консоли и длинные строки. Для 511 коротких строк результат дополнительно сравнивается с независимым простым перебором подстрок. Это помогает проверить больше случаев, чем несколько примеров, выбранных вручную.

## 7. Главные проверки в коде

Первый пример вызывает алгоритм для abba и сравнивает весь ответ: подстроку, длину и количество вхождений. Проверка только длины могла бы пропустить неправильную подстроку или счётчик. Второй пример передаёт число вместо строки в JSON. Он должен вызвать понятную ошибку. Функция deepEqual сравнивает результаты, а throws проверяет ожидаемую ошибку.

**Для подготовки:** на слайде два сценария показаны отдельно, чтобы легче читать. В рабочих файлах tests/algorithm.cjs и tests/json.cjs эти же сценарии регистрируются циклом по таблице примеров. Это не новые дополнительные тесты; число 99 не изменилось.

## 8. Проверка консоли

Этот тест запускает настоящую программу, а затем проверяет её поведение. Код завершения должен быть ноль, в обычном выводе должны быть правильный палиндром и количество вхождений, а поток ошибок должен остаться пустым. Так проверяется не только функция алгоритма, но и запуск приложения целиком.

**В этот момент показать:**

```powershell
npm run test
```

Пока выполняются тесты: «Каждый инструмент запускает те же 99 проверок. Время, которое они показывают в своих отчётах, не используется как основная сравнительная метрика. Для сравнения работает единая внешняя программа измерения». При нехватке времени показать заранее подготовленный журнал, прямо назвав его сохранённым результатом.

## 9. Качество тестов

Большое число тестов само по себе не доказывает их полезность. Поэтому во временные копии программы внесены три ошибки: неправильный выбор при равных длинах, неверный счётчик и удаление пробелов. Каждый фреймворк обнаружил каждую ошибку. Это подтверждает, что соответствующие проверки замечают эти нарушения, но не доказывает отсутствие любых других ошибок.

Все инструменты запускались по очереди на одном компьютере. Использовались три длины нагрузочных строк: сто, тысяча и десять тысяч. Для итоговых значений взята медиана — четвёртый результат из семи после сортировки по величине.

## Разбор фреймворков для ответов

**Раннер — средство запуска тестов, утверждение — проверка условия.** Раннер организует выполнение и выводит результат. Утверждение проверяет условие и сообщает об ошибке через исключение. В проекте все раннеры используют node:assert/strict, чтобы условия сравнения совпадали.

**Термины со слайда.** Mock-функция заменяет зависимость управляемой подменой: например, вместо запроса к серверу возвращает заранее заданный ответ. Hook — функция подготовки или очистки до или после теста. Coverage показывает, какие участки исходного кода выполнялись при тестировании; высокий процент сам по себе не доказывает правильность проверок. Watch повторно запускает тесты при изменении файлов. Worker — отдельный исполнитель тестов. В текущем сравнении подмены, сбор покрытия и режим наблюдения не используются; файлы и консоль проверяются реальными операциями.

**Jest.** В проекте предоставляет глобальные describe и test. Параметр --runInBand выполняет тесты в одном процессе раннера. Преобразования исходников отключены через transform: {}, окружение — node. Наличие у Jest expect, mocks и покрытия не означает, что эти возможности измерены в данной работе. Источник: [конфигурация Jest 30](https://jestjs.io/docs/30.0/configuration).

**Mocha.** Используется интерфейс describe/it. Для утверждений выбрана библиотека Node.js; отдельная Chai не нужна. Обычная function даёт доступ к this.timeout(30000). Hooks beforeEach/afterEach позволяют готовить и очищать состояние вокруг тестов; в данном проекте файловую очистку выполняет общий helper с finally. Источники: [утверждения](https://mochajs.org/features/assertions/), [hooks](https://mochajs.org/features/hooks/).

**Vitest.** Использует инфраструктуру Vite и API, совместимый с Jest. В проекте функции явно импортируются, окружение задано node, используется один worker, параллельное выполнение файлов отключено. Код приложения остаётся CommonJS, адаптер Vitest загружает общий каталог через createRequire. Один worker не делает внутреннее устройство всех раннеров одинаковым: это ограничение конфигурации, которое нужно учитывать. Источники: [возможности Vitest 3](https://v3.vitest.dev/guide/features), [конфигурация](https://v3.vitest.dev/config/).

**Почему Mocha показал меньшие затраты?** Доказанный факт — его меньшие измеренные значения. Связь с меньшими затратами подготовки раннера является интерпретацией; без профилирования нельзя приписать весь выигрыш конкретному внутреннему механизму.

## Что означают строки тестового кода

| Конструкция | Смысл |
|---|---|
| describe('Название', ...) | Группа связанных тестов |
| test(...) или it(...) | Регистрация отдельного теста |
| assert.deepEqual | Строгое глубокое сравнение, поскольку импортирован node:assert/strict |
| assert.equal | Строгое равенство отдельных значений |
| assert.match | Соответствие строки регулярному выражению |
| assert.throws | Ожидаемое исключение, при необходимости проверка сообщения |
| result.status | Код завершения дочернего процесса |
| result.stdout / stderr | Обычный вывод / поток ошибок |

Модульные тесты проверяют функции изолированно. Чтение временного файла с передачей строк алгоритму проверяет интеграцию. Реальный запуск CLI проверяет поведение приложения через внешний интерфейс. Нагрузочные проверки по-прежнему проверяют правильность результата; само измерение ресурсов делает benchmark.py.

## Вопросы, на которых важно не ошибиться

- **Сколько тестов?** 99 зарегистрированных тестов в каждом раннере. 511 входов перебора находятся внутри девяти из них.
- **Есть ли 100% покрытие?** Покрытие не измерялось; такого утверждения в работе нет.
- **Как проверяется пустой вход?** Пустая строка допустима, пустой JSON-пакет запрещён.
- **Зачем общий каталог?** Для одинаковых сценариев и утверждений при сравнении. Все три раннера действительно запускают проверки.
- **Почему не достаточно проверить длину?** Можно получить верную длину, но неверную подстроку или число вхождений.
- **Что доказывает контроль дефектов?** Тесты обнаруживают три выбранных нарушения. Это не доказательство отсутствия любых ошибок.
- **Почему не сравнивать только Duration из вывода раннера?** Границы внутренних измерений могут отличаться; внешний монитор задаёт общую границу полного запуска.
- **CPU больше полного времени — ошибка?** Не обязательно: процессорное время нескольких одновременно работающих процессов суммируется.
- **Что такое RSS?** Резидентная память процессов; её сумма не равна только JS-куче и не гарантирует подсчёт исключительно уникальных физических страниц.
- **Победитель универсален?** Нет. Здесь сравнивается конкретный набор, один файл адаптера на раннер и зафиксированные последовательные конфигурации.
