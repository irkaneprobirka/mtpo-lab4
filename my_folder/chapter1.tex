\section{Математическая постановка проблемы} \label{ch1:math}

Пусть задано множество сравниваемых фреймворков
\[
    F=\{f_1,f_2,f_3\}=\{\text{Jest},\text{Vitest},\text{Mocha}\}.
\]
Для каждого фреймворка $f_i$ запускается один и тот же набор модульных тестов $T(n)$, где $n$ --- размер входных данных. В данной работе $n$ соответствует числу элементов массива, импортируемого из JSON-файла.

Для каждого запуска измеряются три величины:
\[
    \tau_i(n) \text{ --- время выполнения,}
\]
\[
    m_i(n) \text{ --- пиковое потребление оперативной памяти RSS,}
\]
\[
    c_i(n) \text{ --- пиковая загрузка CPU дочернего процесса.}
\]
Тогда результат эксперимента задается матрицей наблюдений
\[
    R(n)=
    \begin{pmatrix}
    \tau_1(n) & m_1(n) & c_1(n)\\
    \tau_2(n) & m_2(n) & c_2(n)\\
    \tau_3(n) & m_3(n) & c_3(n)
    \end{pmatrix}.
\]

Задача сравнения состоит не в поиске абсолютно лучшего инструмента, а в построении воспроизводимого порядка предпочтения по выбранной метрике. Для метрики времени определяется отношение
\[
    f_a \prec_{\tau} f_b \Longleftrightarrow \tau_a(n) < \tau_b(n).
\]
Аналогично вводятся отношения $\prec_m$ и $\prec_c$ для памяти и CPU. Если требуется единый рейтинг, используется нормированная взвешенная оценка:
\[
    S_i = w_{\tau}\frac{\tau_i}{\max_j \tau_j}
        + w_m\frac{m_i}{\max_j m_j}
        + w_c\frac{c_i}{\max_j c_j},
\]
где $w_{\tau}+w_m+w_c=1$. Чем меньше $S_i$, тем предпочтительнее фреймворк при заданных весах. В отчете основной анализ проводится отдельно по каждой метрике, поскольку в реальном проекте приоритеты могут различаться: локальная разработка чувствительнее к скорости, а CI-сервер --- к памяти и CPU.

\section{Сравниваемые фреймворки} \label{ch1:frameworks}

Jest является фреймворком ``из коробки'': он включает раннер, assertions, mock-функции, snapshot-тестирование и средства покрытия. Такой подход удобен для проектов, где важно быстро получить единый стандарт тестирования без отдельного подбора библиотек~\cite{jest-docs}.

Vitest проектировался как быстрый тестовый фреймворк для экосистемы Vite. Его сильная сторона --- близость API к Jest при более легкой интеграции с Vite-конфигурацией и современными ESM-проектами~\cite{vitest-guide,vitest-cli}.

Mocha представляет более модульный подход: сам раннер выполняет тесты, но assertions, spies, stubs и mocks обычно подключаются отдельно. В официальной документации Mocha подчеркивается установка пакета и запуск через \texttt{npx mocha}; требования к версии Node.js следует проверять по документации выбранной версии Mocha~\cite{mocha-getting-started}. Для assertions в проекте выбран Chai, так как это распространенная BDD/TDD-библиотека утверждений для Node.js и браузера~\cite{chai-docs}.

\section{Описание разработанного программного обеспечения} \label{ch1:software}

Для эксперимента разработан компактный проект \texttt{benchmark\_app}. Его назначение --- сформировать одинаковые входные данные, запустить три тестовых фреймворка на одинаковых проверках и сохранить измеренные метрики в машинно-читаемом виде.

Проект имеет следующую структуру:
\begin{lstlisting}[breaklines=true]
benchmark_app/
  package.json
  requirements.txt
  data/author_example.json
  data/reference_input.json
  data/reference_output.json
  src/benchmark.js
\end{lstlisting}

Файл \texttt{requirements.txt} добавлен по требованию задания. Для JavaScript-проекта зависимости фактически задаются в \texttt{package.json}, а \texttt{requirements.txt} фиксирует системные требования: Node.js, npm и команды установки.

Входные данные импортируются из JSON. Каждый файл содержит поле \texttt{size}, задающее размер массива, и поле \texttt{values}, которое может быть неполным. Если \texttt{values} короче \texttt{size}, программа детерминированно дополняет массив. Это обеспечивает переменный размер входа и позволяет быстро строить малые и крупные эксперименты без ручного перечисления всех элементов.

\section{Средства, подходы и методы тестирования} \label{ch1:testing-methods}

Во всех трех фреймворках проверяется одна и та же логика: сортировка чисел, расчет суммы, среднего значения, минимума и максимума. Такой набор выбран потому, что он достаточно прост для ручной проверки, но при увеличении размера входа создает измеримую нагрузку на раннер.

Методика тестирования включает:
\begin{enumerate}
    \item модульные тесты чистых функций обработки массива;
    \item параметризацию размера входа через JSON;
    \item одинаковые assertions для всех фреймворков;
    \item многократный запуск команды тестирования как дочернего процесса;
    \item сбор метрик времени, RSS и CPU средствами Node.js.
\end{enumerate}

Для времени используется \texttt{performance.now()} из модуля \texttt{perf\_hooks}~\cite{node-perf-hooks}. Для памяти применяется наблюдение за RSS процесса, а для CPU --- периодическое считывание процессорного времени дочернего процесса средствами операционной системы. В Node.js также доступны функции \texttt{process.memoryUsage()} и \texttt{process.cpuUsage()}, которые возвращают данные о памяти и CPU текущего процесса~\cite{node-process}.

\section{Алгоритм измерения} \label{ch1:algorithm}

Псевдокод алгоритма приведен в алгоритме~\ref{alg:benchmark}. Он оформлен в окружении \texttt{algorithm}, как требуется в задании.

\begin{algorithm}[h]
\caption{Сравнение Jest, Vitest и Mocha по ресурсным метрикам}
\label{alg:benchmark}
\KwInput{JSON-файл $D$, множество фреймворков $F$, число повторов $k$}
\KwOutput{Таблица результатов $R$}
Загрузить $D$ и сформировать массив $A$ длины $n$\;
Построить эталонный результат $E$ для массива $A$\;
$R \leftarrow \varnothing$\;
\ForEach{$f \in F$}{
    \For{$r \leftarrow 1$ \KwTo $k$}{
        Сформировать команду запуска тестов для $f$\;
        $t_0 \leftarrow$ текущее время\;
        Запустить команду как дочерний процесс\;
        \While{процесс выполняется}{
            измерить текущий RSS процесса\;
            измерить текущую загрузку CPU\;
            обновить пиковые значения\;
        }
        $t_1 \leftarrow$ текущее время\;
        проверить код завершения и совпадение результата с $E$\;
        добавить $(f,r,t_1-t_0,RSS_{max},CPU_{max})$ в $R$\;
    }
}
Сохранить $R$ в JSON и CSV\;
\end{algorithm}

\section{Иллюстративный пример} \label{ch1:example}

Авторский иллюстративный пример хранится в файле \texttt{benchmark\_app/data/author\_example.json}. Его содержимое:
\begin{lstlisting}[breaklines=true]
{
  "name": "author-small",
  "size": 6,
  "values": [5, 1, 4, 1, 3, 2]
}
\end{lstlisting}

Для этого набора эталонный результат вычисляется вручную:
\[
    sort([5,1,4,1,3,2])=[1,1,2,3,4,5],
\]
\[
    sum=16,\quad mean=\frac{16}{6}\approx 2.6667,\quad min=1,\quad max=5.
\]

Таким образом, фреймворк считается успешно прошедшим функциональную проверку, если тест возвращает отсортированный массив \texttt{[1,1,2,3,4,5]}, сумму \texttt{16}, минимум \texttt{1}, максимум \texttt{5} и среднее значение с допустимой погрешностью.

\section{Пошаговое выполнение алгоритма на иллюстративных данных} \label{ch1:steps}

Пошаговое выполнение алгоритма на файле \texttt{author\_example.json} выглядит следующим образом.

\begin{enumerate}
    \item Программа читает JSON-файл и получает массив \texttt{[5,1,4,1,3,2]}.
    \item Размер входа равен \texttt{6}, поэтому дополнение массива не выполняется.
    \item Формируется эталон: сумма \texttt{16}, среднее \texttt{2.6667}, минимум \texttt{1}, максимум \texttt{5}.
    \item Для Jest запускается команда \texttt{npm run test:jest}. Процесс измеряется до завершения.
    \item Для Vitest запускается команда \texttt{npm run test:vitest} с тем же входным файлом.
    \item Для Mocha запускается команда \texttt{npm run test:mocha}; assertions выполняются через Chai.
    \item Для каждого запуска сохраняются время, пиковый RSS и пиковый CPU.
    \item Результаты объединяются в таблицу и сравниваются по трем метрикам.
\end{enumerate}
