\section{Обоснование выбора измеряемой функции} \label{ch4:function}

В качестве тестируемой логики выбрана функция вычисления сводки по числовому массиву. Она сортирует значения, вычисляет сумму, среднее, минимум и максимум. Такой пример удобен по трем причинам.

Во-первых, результат легко проверить вручную на малом массиве. Это важно для эталонного входного файла и демонстрации пошагового выполнения алгоритма.

Во-вторых, размер входа естественно масштабируется. Увеличение \texttt{size} в JSON-файле приводит к увеличению массива без изменения тестового кода.

В-третьих, сама функция не привязана к конкретному тестовому фреймворку. Следовательно, различия в измерениях в большей степени отражают стоимость инфраструктуры Jest, Vitest и Mocha, а не различия в прикладной логике.

\section{Поток данных} \label{ch4:dataflow}

Поток данных в приложении можно описать последовательностью:
\[
    JSON \rightarrow A \rightarrow E \rightarrow TestRunner \rightarrow Metrics \rightarrow Report.
\]
Здесь $A$ --- массив чисел, $E$ --- эталонная сводка, \texttt{TestRunner} --- выбранный фреймворк, а \texttt{Metrics} --- наблюдения времени, памяти и CPU.

При проверке эталона поток завершается раньше:
\[
    JSON_{in} \rightarrow A \rightarrow E_{actual} \equiv E_{expected}.
\]
Если равенство не выполняется, эксперимент не запускается. Такой порядок защищает от ситуации, когда производительность измеряется для некорректной программы.

\section{Импорт JSON и масштабирование входа} \label{ch4:json}

Импорт JSON реализован через стандартный модуль \texttt{fs}. Это уменьшает число зависимостей и делает проект компактнее. Масштабирование входа выполняется детерминированной формулой:
\[
    a_i = (37i + 11) \bmod 1000.
\]
Она используется только для недостающих элементов, если поле \texttt{values} короче \texttt{size}. Благодаря этому файл может содержать короткий начальный фрагмент, но программа все равно построит массив требуемой длины.

\section{Комментарии к измерению ресурсов} \label{ch4:metrics}

Измерение ресурсов тестового процесса в Node.js имеет практические ограничения. Переносимое чтение RSS дочернего процесса по PID различается между Windows, Linux и macOS, поэтому в компактной версии используется приближенная оценка через процесс бенчмарка. Для учебного проекта этого достаточно, чтобы показать методику и структуру данных. В промышленной версии можно заменить этот блок платформенным сборщиком метрик: \texttt{Get-Process} в PowerShell, \texttt{ps} в Linux или библиотекой системного мониторинга.

При этом архитектура программы не меняется: функция запуска команды уже отделена от функции вычисления сводки. Значит, улучшение мониторинга не потребует переписывать тесты Jest, Vitest и Mocha.
