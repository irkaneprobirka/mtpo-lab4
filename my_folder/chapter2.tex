\section{Структура приложения}
Приложение состоит из трёх основных модулей. \code{manacher.js} содержит чистую вычислительную функцию. \code{json-input.js} проверяет формат JSON и читает файл. \code{cli.js} разбирает команды, получает вход и выводит результат. Такое разделение позволяет проверять алгоритм без файловой системы, парсер без терминала, а затем всю цепочку в интеграционных тестах.

JavaScript выполняется напрямую в Node.js, отдельная компиляция приложения не нужна. Рабочая программа не использует сторонних библиотек: достаточно встроенных средств Node.js. Jest, Mocha и Vitest установлены только как средства разработки. Python применяется как внешний измеритель, не входит в логику поиска палиндромов и не нужен для обычного запуска программы.

В коде используются осмысленные имена: \code{characters}, \code{longestLength}, \code{longestStart}, \code{position}. Операции обновления центра, границы и максимума записаны отдельными блоками. Комментарии объясняют, почему нужен массив кодовых точек, зачем используются уникальные границы и почему строгое сравнение сохраняет левый ответ. Они описывают причины решений, а не повторяют каждую строку программы.

\section{Работа с консолью и JSON}
Программа поддерживает небольшое число команд. Это уменьшает количество правил, которые должен помнить пользователь:
\begin{lstlisting}
npm run start
npm run start -- "abba"
npm run start -- --text "abba"
npm run start -- --file data/example.json
npm run start -- --help
\end{lstlisting}
Без аргументов в интерактивном терминале программа предлагает ввести строку. При перенаправлении стандартного ввода она читает весь поток. Параметр \code{--text} нужен, в частности, для пустой строки или текста, похожего на параметр. Параметр \code{--file} принимает путь к JSON-файлу; другие форматы импорта не поддерживаются.

Единственная схема файла имеет объект с непустым массивом \code{strings}. Каждый его элемент -- строка:
\begin{Verbatim}[fontsize=\small,frame=single]
{"strings": ["abba", "топот", ""]}
\end{Verbatim}
Ожидаемые ответы не являются частью пользовательского входа. Программа должна вычислить их самостоятельно. Пустая строка допустима внутри массива, а пустой массив отклоняется: файл должен содержать хотя бы одну задачу. Повторяющиеся строки разрешены и обрабатываются независимо.

Парсер не удаляет пробелы и переводы строк. Регистр также сохраняется. Для строкового ввода перевод строки в перенаправленном потоке является частью задачи. Маркер UTF-8 BOM удаляется при чтении JSON, поскольку некоторые текстовые редакторы добавляют его в начало файла. Проверка расширения не зависит от регистра, поэтому \code{.JSON} и \code{.json} допустимы.

Для \code{abba} вывод имеет вид:
\begin{Verbatim}[fontsize=\small,frame=single]
Строка: "abba"
Самый длинный палиндром: "abba"
Длина: 4
Число палиндромных вхождений: 6
\end{Verbatim}
Строки в выводе заключаются в кавычки с помощью JSON-экранирования. Поэтому пользователь видит, где находятся пробелы, кавычки и управляющие символы. Перевод строки внутри входа не нарушает расположение подписей результата.

Неверный JSON, неправильный тип элемента, неизвестная команда и ошибка чтения файла приводят к сообщению на русском языке и коду завершения 1. Весь пакет проходит валидацию до вычисления результатов: при ошибке во втором элементе программа не успевает вывести ответ для первого. Это поведение проверяется отдельным интеграционным тестом.

\section{Организация одинаковых тестов}
Тесты разделены по назначению, а не скопированы в три каталога. Общий модуль последовательно регистрирует группы алгоритма, JSON, консоли и нагрузки. Адаптер Jest передаёт функции \code{describe} и \code{test}, адаптер Mocha -- \code{describe} и \code{it}, адаптер Vitest импортирует API из своего пакета. Каждый вызов регистрации создаёт самостоятельный тест с русским названием.

\begin{table}[H]\centering
\caption{Состав полного набора для каждого фреймворка}
\begin{tabular}{lr}\toprule
Группа & Число тестов\\\midrule
Алгоритм Манакера & 47\\
Импорт JSON и файловая система & 25\\
Консольное приложение & 18\\
Отдельный эталонный файл & 1\\
Масштабируемая нагрузка & 8\\\midrule
Всего & 99\\\bottomrule
\end{tabular}
\end{table}

Одинаковое количество тестов само по себе не доказывает одинаковую работу. В данном проекте совпадают также тела проверок, входы, ожидаемые значения и число повторов. Общий каталог устраняет риск того, что один из трёх вручную скопированных файлов позже получит дополнительную проверку, а остальные останутся прежними.

При этом сравниваются реальные раннеры: каждый инструмент обнаруживает свой тестовый файл, создаёт собственное окружение, выполняет зарегистрированные проверки и формирует итог. Общий модуль не подменяет раннер и не измеряет только стандартную библиотеку утверждений. Его назначение -- сохранить одинаковую полезную работу.

Тайм-аут отдельного теста равен 30 секундам. Он используется как предел отказа, а не как желательное время работы. Внешний измеритель имеет отдельный предел длительности процесса. Реальные журналы позволяют различить ошибку утверждения, некорректный вход, проблему установки и превышение времени.

\section{Функциональные и граничные проверки алгоритма}
Двадцать шесть тестов используют явно заданные ожидания. Среди них пустая строка, один символ, чётные и нечётные палиндромы, повторяющиеся символы, отсутствие длинного палиндрома, вложенные палиндромы и максимум у края строки. Для каждого случая проверяются сразу подстрока, длина и счётчик вхождений.

Например, для \code{abba} правильный объект содержит палиндром \code{abba}, длину 4 и счётчик 6. Проверка только длины была бы слабее: неверная подстрока той же длины могла бы остаться незамеченной. Проверка только непустого результата не обнаружила бы большую часть ошибок. Поэтому применяется строгое сравнение полного объекта результата.

Отдельные случаи фиксируют правила Unicode. В строке с двумя одинаковыми эмодзи длина равна двум кодовым точкам, хотя представление UTF-16 содержит больше кодовых единиц. Кириллические примеры проверяют работу с русским текстом. Символ с комбинируемым знаком не нормализуется; тест закрепляет именно такое поведение, чтобы будущая правка не изменила смысл задачи незаметно.

Шесть негативных тестов передают значения неправильного типа: \code{null}, \code{undefined}, число, логическое значение, массив и объект. Проверяется не просто наличие исключения, а его тип и понятное сообщение. Функция не должна молча приводить число к строке или принимать массив за пользовательский текст.

Девять тестов сравнивают алгоритм с независимым перебором всех двоичных строк длины от нуля до восьми. Всего рассматривается 511 строк. Медленный эталон перебирает подстроки и сравнивает их с обращением. Он не использует радиусы или зеркальные индексы Манакера, поэтому ошибка в основном алгоритме с меньшей вероятностью повторится в проверяющем коде.

Пять тестов используют свойство сохранения числа палиндромных вхождений при обращении строки. Проверяется счётчик, а не значение левого максимума: после обращения при равных длинах левым может стать другой палиндром. Ещё один тест запускает функцию несколько раз на разных строках и подтверждает, что предыдущее вычисление не влияет на последующее.

\section{Тестирование JSON и интерфейса}
Проверки JSON охватывают правильные и неправильные документы, а также чтение реальных файлов. Положительные сценарии включают одиночный вход, пакет, пустую строку, пробелы, перевод строки, кавычки, эмодзи, повторяющиеся значения и BOM. Отрицательные -- повреждённый документ, отсутствие \code{strings}, пустой пакет и элементы неправильных типов.

Каждый дефектный документ вынесен в отдельный тест. Если парсер перестанет отклонять число во втором элементе массива, отчёт раннера покажет конкретное название сценария. Один большой тест с десятком несвязанных проверок дал бы менее точную диагностику и прекратил бы выполнение после первой ошибки.

Файловые проверки создают временный каталог и удаляют его в блоке \code{finally}. Таким образом, тесты не зависят от заранее существующих временных файлов и не оставляют мусор после отказа. Отдельно проверяются отсутствующий файл, запрещённое расширение, регистр расширения и передача прочитанных строк вычислительной функции.

Тесты интерфейса проверяют разбор аргументов и форматирование результата как обычные функции. Восемь сценариев дополнительно запускают настоящий процесс \code{cli.js}. Для него проверяются код выхода, стандартный вывод и поток ошибок. Это позволяет обнаруживать дефекты точки входа, которые не видны при отдельной проверке парсера.

В дочерних запусках используются строка, пустая строка, JSON-пакет, перенаправленный поток, справка и три вида ошибок. Для успешного обычного ввода поток ошибок должен быть пустым. Для недопустимого JSON не допускается частичный успешный вывод. Тайм-аут дочернего процесса защищает набор от зависания.

\section{Контрольные дефекты и качество проверок}
Прохождение всех тестов показывает соответствие проверенным ожиданиям, но само по себе не гарантирует, что набор чувствителен к дефектам. Для дополнительной проверки подготовлены три намеренные ошибки. Они вносятся только во временные копии приложения; рабочие исходники не меняются.

Первая ошибка заменяет строгое сравнение максимальной длины на нестрогое. Тогда при равных длинах выбирается более поздний палиндром. Вторая добавляет лишнее вхождение на каждом центре и нарушает счётчик. Третья обрезает пробелы при чтении JSON и меняет пользовательские данные.

\begin{table}[H]\centering\small
\caption{Контрольные дефекты и проверяемое поведение}
\begin{tabularx}{\linewidth}{lX}\toprule
Дефект & Ожидаемый сигнал тестов\\\midrule
Правый максимум вместо левого & Нарушение ответа для \code{babad}\\
Лишние вхождения & Несовпадение счётчика для \code{abba}\\
Обрезка пробелов & Изменение строки при импорте JSON\\\bottomrule
\end{tabularx}
\end{table}

Скрипт запускает каждый дефект под каждым раннером. Для успешной контрольной проверки требуется ненулевой код выхода, сообщение об ошибке утверждения и наличие ожидаемого сценария в журнале. Простая ошибка установки зависимостей не считается обнаруженным дефектом. Результаты сохраняются отдельно от измерений производительности.

Эта процедура представляет ограниченную проверку на трёх выбранных мутациях. Она не является полным мутационным анализом и не позволяет заявлять универсальный процент качества тестов. Также в работе не приводится неподтверждённый процент покрытия кода. Обоснование качества опирается на спецификацию, независимый эталон, классы входов, интеграционные проверки и фактически обнаруженные контрольные ошибки.

\section{Установка и запуск}
Для программы и трёх фреймворков требуется Node.js версии не ниже 22 с npm. Зависимости закреплены в \code{package-lock.json}. Из каталога проекта:
\begin{lstlisting}
cd benchmark_app
npm ci
npm run verify
npm run demo
npm run test
\end{lstlisting}
Команда \code{npm run test} последовательно запускает Jest, Mocha и Vitest. Можно выполнить любой раннер отдельно:
\begin{lstlisting}
npm run test:jest
npm run test:mocha
npm run test:vitest
\end{lstlisting}
Каждая команда регистрирует 99 тестов на стандартном входе. \code{npm run verify} сравнивает вычисленные результаты с отдельным эталонным файлом. Установка Python не требуется для этих действий.

Для замеров дополнительно требуется установленный Python не ниже 3.10. Пользователь работает только с npm-командами. При первом запуске служебный файл \code{scripts/python.js} автоматически создаёт окружение и устанавливает psutil из \code{requirements.txt}. Подготовка не входит в измеряемое время.
\begin{lstlisting}
npm run test:quality
npm run benchmark
npm run results
\end{lstlisting}
Команда \code{npm run benchmark} выполняет полную серию из 63 измерений, а \code{npm run results} выводит таблицу последней завершённой серии. Для короткого показа доступна \code{npm run benchmark:quick}: три измерения на одном размере. Этот режим не заменяет полную серию. Наблюдатель создаёт новый каталог с датой и временем; существующая серия не перезаписывается. Параметры передаются после двойного дефиса в npm-команде.

Масштаб входа меняется генератором:
\begin{lstlisting}
npm run generate
npm run generate -- 200 2000 20000
npm run benchmark -- --input data/size-200.json
\end{lstlisting}
В каждом файле находятся восемь реальных строк. Генератор меняет их длину, а число тестов остаётся постоянным. Стандартная серия использует длины 100, 1000 и 10000. В нагрузочных тестах ожидаемые значения рассчитываются независимыми формулами для однородных и чередующихся строк; произвольный пользовательский файл не подменяет этот специально определённый экспериментальный набор.

Для пересборки отчёта используется \code{My_practice.tex} с исходной преамбулой СПбПУ. Основной текст расположен в \code{my_folder}. Отчёт собирается pdfLaTeX, презентация -- XeLaTeX, библиография -- Biber. Команда \code{build.ps1} из корня проекта выполняет необходимые проходы. Готовые PDF можно читать без установки LaTeX.
